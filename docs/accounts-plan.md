# Accounts branch: investigation

Status: proposal, nothing built yet. Covers Discord login, per-user data, and
the first three features (Book of Shadows, rituals, correspondences).

## What changes

Today the app has no backend: one statically prerendered page, all state in
`localStorage`, all astronomy computed in the browser. Accounts mean adding a
database, server-side sessions and authenticated routes. The goal is to add
those **without touching how `/` works for signed-out visitors**: the
dashboard stays prerendered with ISR, hydration-safe, and fully usable with no
account.

```
/                  unchanged: static shell + client Dashboard
/correspondences   public library built from src/data (no login needed)
/book              Book of Shadows (signed in, dynamic)
/rituals           ritual templates (signed in, dynamic)
/settings          account, synced preferences, export, delete
/api/auth/[...all] auth library route handler
```

The only thing `/` gains is a small account button. It must not read the
session cookie during prerender, so it is either a client component that asks
`/api/auth/get-session` after mount (simplest, matches the existing
"`now = null` until mounted" pattern) or a server island behind `<Suspense>`.

## Stack choices

| Concern | Recommendation | Why |
| --- | --- | --- |
| Auth | **Better Auth** | Listed in the Next 16 auth guide, first-class Discord provider, database sessions, Drizzle adapter, works with the `proxy.ts` convention (Next 16 renamed `middleware.ts` to `proxy.ts`). Auth.js v5 is the alternative but has been in beta for years. |
| Database | **Postgres on Neon** via the Vercel Marketplace | Free tier, branches per Vercel preview deployment, env vars injected automatically. |
| ORM / migrations | **Drizzle** | Typed schema in TS, plain SQL migrations, small runtime, fits the "keep it typed so `tsc` catches gaps" style already used in `src/data`. |
| Validation | Zod | For Server Action inputs. |
| Editor | Plain `<textarea>` with Markdown, rendered with `react-markdown` | Start simple; a rich editor can come later. |

Discord OAuth scope: `identify` only (plus `email` if we want a contact
address). If this is meant for a specific community, add `guilds` and allow
sign-in only for members of a given server ID; that is a one-line check in
the sign-in callback.

Proxy (`src/proxy.ts`) only does optimistic redirects for `/book`,
`/rituals`, `/settings` based on the cookie. Real authorization happens in
each Server Action / data function (`requireUser()`), per the Next guide.

## Data model (first cut)

Auth tables (`user`, `session`, `account`, `verification`) are generated by
Better Auth. App tables:

```ts
user_settings   userId PK, timezone text, hemisphereOverride 'north'|'south'|null

bos_entry       id, userId, kind ('journal'|'ritual'|'spell'|'dream'|'divination'|'craft'),
                title, body (markdown), day (CalendarDay 'YYYY-MM-DD'),
                createdAt, updatedAt, tags text[],
                sky jsonb      -- snapshot: phase, illumination, moon sign,
                               -- nearest sabbat, Mercury Rx; from buildDashboardModel

ritual          id, userId, title, purpose, materials text[], steps text[],
                timing jsonb   -- e.g. { phases: ['Full Moon'], sabbats: ['Samhain'] }
                createdAt, updatedAt

user_correspondence  id, userId, category ('herb'|'crystal'|'colour'|'deity'|...),
                     name, properties text[], notes, links to phase/sign/sabbat keys
```

Notes:

- `day` is a `CalendarDay` derived with `dayOf(instant, userTimezone)`, the
  same time model as `src/lib/days.ts`. Never a server-local midnight.
- The `sky` snapshot is the nice tie-in: every entry is automatically stamped
  with the moon phase, moon sign and wheel position at the moment it was
  written, so the Book of Shadows can be browsed by lunation or sabbat.
  `buildDashboardModel` is pure, so it runs on the server unchanged.
- Correspondence keys reuse the unions in `src/lib/names.ts`, so links from a
  user's notes to `MOON_CORRESPONDENCES` etc. stay type-checked.

## Features, in order

1. **Foundation.** Better Auth + Discord, Neon + Drizzle, `/settings` with
   sign out and delete account. Timezone moves from `localStorage` to
   `user_settings` when signed in (local value is still the fallback and is
   imported on first sign-in).
2. **Correspondences library** (`/correspondences`). Public, read-only pages
   generated from the existing `src/data` files: browse by phase, sign,
   sabbat, herb, crystal, colour. No accounts needed, so this could ship to
   `main` independently. Signed-in users then get personal notes and their
   own entries alongside the curated ones.
3. **Book of Shadows** (`/book`). Create, edit, delete entries; list view and a
   "by moon" view grouped into lunations. The Daily Craft card gets a
   "log this" button that opens a prefilled entry, which closes the loop on
   the existing `book-of-shadows` craft activity. Export to Markdown/JSON
   from day one, since this is personal writing.
4. **Rituals** (`/rituals`). Templates with materials, steps and preferred
   timing. The timeline can then show "your Full Moon ritual" on the matching
   event, and "perform" creates a `ritual` Book of Shadows entry from the
   template.

Later ideas: sharing a ritual by link, a coven/group space keyed to a Discord
server, Discord DM reminders before an esbat or sabbat (needs a bot, not just
OAuth).

## Privacy

A Book of Shadows is personal. Entries are private by default with no public
or shared mode in the first version. Account deletion removes all rows
(cascade on `userId`), and export is available before deletion. Neon encrypts
at rest; end-to-end encryption would block server-side search and the sky
snapshot, so it is not proposed for v1.

## Impact on existing rules and CI

- `AGENTS.md` "no backend, no DB" changes for this branch; the orientation
  needs a new section on server code (`src/server/`: db, auth, actions).
- Hydration rules still apply to every page that renders dates: entry dates
  are `CalendarDay` strings formatted with `formatDay`, instants are rendered
  client-side or with an explicit zone.
- CI needs a Postgres service container (or PGlite in tests) and migrations
  run before e2e. Playwright tests sign in by seeding a session row rather
  than driving Discord.
- New env vars: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`,
  `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`. A Discord application is
  needed with redirect URLs for localhost, previews and production.

## Branching

A long-lived branch will drift from `main` as the dashboard keeps changing.
Better: land work on `main` in small PRs where nothing is linked from `/`
until it is ready (the routes simply exist), or behind a `NEXT_PUBLIC_ACCOUNTS`
flag. The correspondences library can go straight to `main`.
