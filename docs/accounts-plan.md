# Accounts branch: investigation

Status: step 1 (foundation) built, behind a flag. Covers Discord login,
per-user data, and the next three features (Book of Shadows, rituals,
correspondences).

Decisions so far: sign-in is for members of one Discord server only (small
audience); Postgres on Neon via Vercel; timezone syncs across devices
(Discord doesn't expose a user's timezone, only their language, so the
choice made in the dashboard is what syncs); Book of Shadows uses Markdown.

## What changes

Today the app has no backend: one statically prerendered page, all state in
`localStorage`, all astronomy computed in the browser. Accounts mean adding a
database, server-side sessions and authenticated routes. The goal is to add
those **without touching how `/` works for signed-out visitors**: the
dashboard stays prerendered with ISR, hydration-safe, and fully usable with no
account.

```
/                  unchanged: static shell + client Dashboard
/correspondences   public library built from src/data (no login needed)
/book              Book of Shadows (signed in, dynamic)
/rituals           ritual templates (signed in, dynamic)
/settings          account, synced preferences, export, delete
/api/auth/[...all] auth library route handler
```

The only thing `/` gains is an avatar in the header (signed in) or a
"Members' sign in" link in the footer (signed out). Both come from `/api/me`,
fetched after mount, matching the existing "`now = null` until mounted"
pattern, so the session cookie is never read while rendering `/`.

## Stack choices

| Concern | Recommendation | Why |
| --- | --- | --- |
| Auth | **Better Auth** | Listed in the Next 16 auth guide, first-class Discord provider, database sessions, Drizzle adapter, works with the `proxy.ts` convention (Next 16 renamed `middleware.ts` to `proxy.ts`). Auth.js v5 is the alternative but has been in beta for years. |
| Database | **Postgres on Neon** via the Vercel Marketplace | Free tier, branches per Vercel preview deployment, env vars injected automatically. |
| ORM / migrations | **Drizzle** | Typed schema in TS, plain SQL migrations, small runtime, fits the "keep it typed so `tsc` catches gaps" style already used in `src/data`. |
| Validation | Zod | For Server Action inputs. |
| Editor | Plain `<textarea>` with Markdown, rendered with `react-markdown` | Start simple; a rich editor can come later. |

Discord OAuth scopes: `identify`, `email` (Better Auth requires an email)
and `guilds.members.read`. On every sign-in the server asks Discord
`GET /users/@me/guilds/{DISCORD_GUILD_ID}/member` with the user's own token;
anything but a 200 refuses the sign-in (`src/server/discord.ts`). No bot is
needed. Someone who leaves the server keeps access until their session
expires (30 days).

No `proxy.ts`: each page and Server Action calls `requireUser()` /
`getCurrentUser()`, which is the real check per the Next guide. Sign-in, sign
out and account deletion are Server Actions, so there is no client-side auth
library.

## Data model (first cut)

Auth tables (`user`, `session`, `account`, `verification`) are generated by
Better Auth. App tables:

```ts
user_settings   userId PK, timezone text, hemisphereOverride 'north'|'south'|null

bos_entry       id, userId, kind ('journal'|'ritual'|'spell'|'dream'|'divination'|'craft'),
                title, body (markdown), day (CalendarDay 'YYYY-MM-DD'),
                createdAt, updatedAt, tags text[],
                sky jsonb      -- snapshot: phase, illumination, moon sign,
                               -- nearest sabbat, Mercury Rx; from buildDashboardModel

ritual          id, userId, title, purpose, materials text[], steps text[],
                timing jsonb   -- e.g. { phases: ['Full Moon'], sabbats: ['Samhain'] }
                createdAt, updatedAt

user_correspondence  id, userId, category ('herb'|'crystal'|'colour'|'deity'|...),
                     name, properties text[], notes, links to phase/sign/sabbat keys
```

Notes:

- `day` is a `CalendarDay` derived with `dayOf(instant, userTimezone)`, the
  same time model as `src/lib/days.ts`. Never a server-local midnight.
- The `sky` snapshot is the nice tie-in: every entry is automatically stamped
  with the moon phase, moon sign and wheel position at the moment it was
  written, so the Book of Shadows can be browsed by lunation or sabbat.
  `buildDashboardModel` is pure, so it runs on the server unchanged.
- Correspondence keys reuse the unions in `src/lib/names.ts`, so links from a
  user's notes to `MOON_CORRESPONDENCES` etc. stay type-checked.

## Features, in order

1. **Foundation. Done.** Better Auth + Discord (server members only),
   Drizzle + Postgres, `/signin`, `/settings` with sign out and delete
   account. A signed-in user's timezone is saved to `user_settings` and
   applied on every device. An account with no zone yet adopts whatever the
   dashboard is showing on the first signed-in visit (members found having
   to re-pick an already-correct zone confusing); later changes on any
   device update it.
2. **Correspondences library** (`/correspondences`). Public, read-only pages
   generated from the existing `src/data` files: browse by phase, sign,
   sabbat, herb, crystal, colour. No accounts needed, so this could ship to
   `main` independently. Signed-in users then get personal notes and their
   own entries alongside the curated ones.
3. **Book of Shadows** (`/book`). Create, edit, delete entries; list view and a
   "by moon" view grouped into lunations. The Daily Craft card gets a
   "log this" button that opens a prefilled entry, which closes the loop on
   the existing `book-of-shadows` craft activity. Export to Markdown/JSON
   from day one, since this is personal writing.
4. **Rituals** (`/rituals`). Templates with materials, steps and preferred
   timing. The timeline can then show "your Full Moon ritual" on the matching
   event, and "perform" creates a `ritual` Book of Shadows entry from the
   template.

Later ideas: sharing a ritual by link, a coven/group space keyed to a Discord
server, Discord DM reminders before an esbat or sabbat (needs a bot, not just
OAuth).

## Privacy

A Book of Shadows is personal. Entries are private by default with no public
or shared mode in the first version. Account deletion removes all rows
(cascade on `userId`), and export is available before deletion. Neon encrypts
at rest; end-to-end encryption would block server-side search and the sky
snapshot, so it is not proposed for v1.

## Impact on existing rules and CI

- `AGENTS.md` "no backend, no DB" changes for this branch; the orientation
  needs a new section on server code (`src/server/`: db, auth, actions).
- Hydration rules still apply to every page that renders dates: entry dates
  are `CalendarDay` strings formatted with `formatDay`, instants are rendered
  client-side or with an explicit zone.
- CI needs a Postgres service container (or PGlite in tests) and migrations
  run before e2e. Playwright tests sign in by seeding a session row rather
  than driving Discord.
- New env vars: see `.env.example` and "Setup" below.

## Setup (to switch accounts on)

Discord only accepts exact redirect URLs, and every Vercel deployment gets a
new random URL, so sign-in can't work on those per-deployment links. Vercel
also gives each branch a **stable** URL that always points at its latest
deployment:

    https://<project>-git-<branch>-<team>.vercel.app

(shown on the deployment page under "Domains"). That is the test address.
Testing happens in three places:

- **Automated tests** never touch Discord (they seed sessions), so CI needs
  none of this.
- **Locally** (`npm run dev`) with the real Discord login.
- **A preview branch** on its stable URL, before switching production on.

1. **Discord application.** At https://discord.com/developers/applications
   create an application. Under OAuth2, copy the Client ID and Client Secret
   and add these redirect URLs:
   - `http://localhost:3000/api/auth/callback/discord`
   - `https://<branch URL>/api/auth/callback/discord` (one per test branch)
   - `https://<production domain>/api/auth/callback/discord`
2. **Server ID.** In Discord, turn on Developer Mode (Settings, Advanced),
   right-click the server, Copy Server ID.
3. **Database.** In the Vercel project, Storage, add Neon (Postgres). It sets
   `DATABASE_URL`, and gives each preview its own database branch, so test
   accounts never mix with real ones.
4. **Environment variables.** In Vercel, Settings, Environment Variables,
   for **Preview and Production**:
   - as **Config**: `DISCORD_CLIENT_ID`, `DISCORD_GUILD_ID`
   - as **Secret**: `DISCORD_CLIENT_SECRET`, `BETTER_AUTH_SECRET`
     (`openssl rand -base64 32`)
   - as **Secret**, Production only: `CRON_SECRET` (same command). Vercel
     Cron sends it to `/api/cron/purge-logs` (scheduled in `vercel.json`),
     which deletes sign-in and visit logs older than 90 days; without it the
     purge refuses every request. Crons run only on production.

   Accounts switch on in any build that has these plus `DATABASE_URL`
   (`next.config.ts`), and the sign-in address is worked out from Vercel's
   system variables (`src/server/baseUrl.ts`): the branch URL in previews,
   the production domain in production. Nothing changes in production
   until this code is merged.
5. **Test**: redeploy the branch and sign in **on the branch URL**, not the
   per-deployment link. Then merge; `vercel-build` applies migrations to the
   production database, then builds.

Always sign in on the branch URL or the production domain: on any other
address (another alias, a per-deployment link) Discord rejects the redirect.
Previews of other branches also get accounts switched on, but sign-in there
fails until their branch URL is added to the Discord app.

Vercel's Deployment Protection puts previews behind a Vercel login by
default. That's fine for you; other members testing a preview would need it
relaxed for that branch.

If testing on many branches becomes routine, Better Auth's `oauthProxy`
plugin can route every preview's sign-in through production instead. Not
worth it for now.

Locally: copy `.env.example` to `.env.local`, point `DATABASE_URL` at any
Postgres, `npm run db:migrate`, `npm run dev`.

## Branching

A long-lived branch will drift from `main` as the dashboard keeps changing.
Better: land work on `main` in small PRs where nothing is linked from `/`
until it is ready (the routes simply exist). The correspondences library can go straight to `main`.
